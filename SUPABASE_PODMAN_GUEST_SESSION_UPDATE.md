# Guest Session Persistence Update

This file is an **authoritative requirements update** to `SUPABASE_PODMAN_IMPLEMENTATION_PLAN.md`. Where the earlier plan says application authentication is mandatory, this update supersedes it.

## Revised product requirement

Authentication is optional.

The application must support two storage modes:

```text
Guest browser session
    -> fully functional temporary workspace
    -> survives page refresh
    -> upload/download/translate/edit all work
    -> not recoverable after the browser session ends
    -> server files are cleaned later by bounded TTL cleanup

Authenticated Supabase user
    -> durable user-owned workspace
    -> survives browser closure, restart, and later sign-in
    -> can be reopened from another authenticated browser/device
```

Signing up or signing in is therefore an **opt-in persistence feature**, not a prerequisite for using PYTHONPathFinder.

## 1. Guest workspace identity

Reuse the existing anonymous workspace mechanism rather than inventing another temporary-storage subsystem, but change its lifetime semantics.

A guest receives a cryptographically random opaque workspace ID generated by the backend. It is stored in an HTTP-only **session cookie** such as the existing `vg2c_workspace` cookie.

Important change from the current code:

- do **not** set `Max-Age` or `Expires` on the guest cookie;
- the cookie should be a browser-session cookie;
- `HttpOnly` remains enabled;
- `SameSite=Lax` remains appropriate;
- `Secure=true` should be used once HTTPS is introduced.

A normal page refresh therefore sends the same session cookie and resolves the same temporary workspace.

When the browser session ends, the browser normally discards the session cookie, so a subsequent new browser session receives a new guest workspace and cannot recover the old one.

Browser caveat: some browsers/session-restore configurations may restore session cookies after a browser restart. Web applications cannot reliably receive an event proving a browser was closed. The security/property that must be enforced server-side is therefore that an old guest workspace is accessible only to possession of its high-entropy session token and is automatically deleted after a short inactivity TTL. If strict tab-close semantics are ever required, that is a different requirement and should use a tab-scoped mechanism such as `sessionStorage` instead.

## 2. Guest storage path

Temporary guest data remains separated from authenticated data:

```text
/data/guest-workspaces/<opaque-random-session-id>/
  inputs/
  generated/
```

Authenticated durable data remains:

```text
/data/users/<supabase-user-uuid>/
  inputs/
  generated/
```

Never place guest and authenticated workspaces in the same namespace.

## 3. Guest cleanup

Guest workspaces are temporary server-side data and need bounded cleanup because the server cannot know exactly when a browser closes.

Retain inactivity cleanup **only for guest workspaces**.

Recommended behavior:

- refresh/touch the guest workspace on successful guest API activity;
- remove guest workspaces after a configurable inactivity period;
- current 24-hour retention is acceptable as an initial cleanup safety window, but it does not mean the user can recover the workspace after closing the browser;
- the guest cookie itself remains session-only and must not receive a 24-hour `Max-Age`.

Authenticated `/data/users/<uuid>` directories must never be deleted by guest cleanup.

Configuration should distinguish the purpose clearly, e.g.:

```text
VG2C_GUEST_RETENTION_SECONDS=86400
VG2C_GUEST_CLEANUP_INTERVAL_SECONDS=3600
```

Do not reuse an ambiguously named authenticated-workspace retention setting.

## 4. Request identity precedence

For each protected/data API request, resolve identity in this order:

1. If a valid Supabase Bearer token is present, use the authenticated user workspace.
2. Otherwise, use/create the guest browser-session workspace.

An invalid/expired Bearer token must **not** silently fall back to guest mode for that request. Return `401` so a broken authenticated session cannot accidentally save work into a temporary guest workspace.

No API should accept a client-supplied user UUID or filesystem root.

## 5. Backend request scope

The existing request-scoped `DocumentStore` design still fits both modes.

Conceptually:

```text
request
  |
  +-- valid Bearer token --> AuthService --> /data/users/<uuid>/
  |
  +-- no Bearer token --------------------> /data/guest-workspaces/<session-id>/
                                              |
                                              v
                                        DocumentStore
```

`DocumentStore` must remain unaware of authentication. It receives one already-authorized root and continues enforcing path containment below it.

`WorkspaceManager` should retain the shared path/upload/quota logic and provide two explicit resolution paths rather than duplicating the implementation:

```python
resolve_guest(session_id: str | None) -> tuple[Workspace, bool]
resolve_user(user_id: UUID) -> Workspace
```

Shared safe-path, upload, listing, quota and file-resolution code remains DRY.

## 6. Frontend behavior

### Guest startup

The application opens directly into the existing workspace UI. It must not force an Auth gate before upload/translation.

Show an unobtrusive persistence action such as:

```text
Temporary session — Sign in to save your files
```

Guest users can:

- upload files/folders;
- list files;
- translate;
- open/edit/save generated output;
- preview CSV;
- download individual files;
- download workspace ZIP;
- refresh the page without losing the current session workspace.

### Signed-in state

When authenticated, display that the workspace is saved/persistent and offer sign out.

The Auth client continues to own session restoration and refresh for signed-in users.

### API helper

`authorizedFetch()` should become an identity-aware request helper rather than requiring authentication for every request:

- if an Auth session exists, attach `Authorization: Bearer <token>`;
- if no Auth session exists, make the request without the header and allow the HTTP-only guest cookie to identify the temporary workspace;
- if a request carrying a Bearer token receives `401`, attempt at most one normal token refresh/retry if appropriate; do not retry anonymously.

Raw protected download anchors remain problematic for authenticated users because they cannot attach a Bearer header. Use authenticated/blob download helpers for a consistent implementation in both modes.

## 7. Sign-up/sign-in and temporary-workspace promotion

Signing in should not unexpectedly discard work already created as a guest.

Recommended simple promotion behavior:

1. Browser has guest session cookie and guest files.
2. User signs up/signs in successfully.
3. The next authenticated request contains both:
   - valid Bearer token;
   - existing guest session cookie.
4. Backend resolves the authenticated user.
5. If the user's durable workspace is new/empty, atomically move/copy the guest workspace contents into `/data/users/<uuid>/` and retire the guest workspace.
6. If the durable workspace already contains files:
   - never overwrite persistent files automatically;
   - merge only non-conflicting relative paths;
   - identical-content conflicts may be treated as already present;
   - different-content conflicts remain in the temporary workspace and are reported to the user for explicit resolution.

Keep this promotion logic narrow and filesystem-based. Do not add database metadata merely to implement promotion.

Signing out switches subsequent requests back to a fresh/remaining guest session. It must not expose the signed-in user's durable files through guest mode.

## 8. Revised security invariants

Authenticated users:

> An authenticated user must never be able to read, modify, enumerate, overwrite, delete, download, archive, or otherwise access another authenticated user's persisted workspace or data.

Guests:

> A guest session must never be able to access another guest session's temporary workspace or any authenticated user's durable workspace.

Cross-mode:

> Guest identity and authenticated identity are separate namespaces, and invalid authentication must never downgrade silently into guest access for the same request.

## 9. Revised tests

### Guest lifecycle

- first guest request creates temporary workspace;
- upload/list/translate/edit/download all work without login;
- page refresh sees the same files;
- a separate browser profile cannot see the first guest's files;
- a new browser session without the old session cookie cannot recover the prior guest workspace;
- expired guest workspace is removed by cleanup;
- guest cleanup never touches `/data/users`.

### Authenticated persistence

- signup/signin creates/resolves durable `/data/users/<uuid>` workspace;
- browser close/reopen + sign in restores files;
- application stack restart preserves files;
- second authenticated user cannot access them.

### Guest -> authenticated promotion

- guest creates files, signs up, files become durable;
- refresh/restart/signin still shows promoted files;
- promotion never overwrites a differing existing durable file;
- promotion cannot move another guest's workspace;
- stale/forged guest cookie cannot escape guest namespace.

### Signout

- signout removes access to authenticated workspace from subsequent guest requests;
- persistent files remain on disk for the user;
- guest mode starts/continues in its own temporary workspace.

## 10. Changes to the earlier implementation plan

The following statements in `SUPABASE_PODMAN_IMPLEMENTATION_PLAN.md` are superseded:

- "Anonymous application access after migration" is **no longer a non-goal**; guest application access is required.
- Protected/data APIs are **not authentication-required** when no Bearer token is supplied; they use guest session isolation instead.
- The `vg2c_workspace` concept is **not removed entirely**; it remains as a session-only guest identifier.
- Anonymous random workspace generation remains for guest mode.
- Retention cleanup remains for guest data only.
- `VG2C_WORKSPACE_RETENTION_SECONDS` / cleanup settings should be replaced with explicitly guest-named equivalents rather than removed outright.
- The frontend must **not** be gated behind sign-in.
- Authentication is the switch from temporary to durable persistence, not the switch that enables application functionality.

Supabase services and Podman conclusions remain unchanged: local Postgres + Supabase Auth are sufficient, Supabase Storage remains unnecessary, and one Compose-compatible stack should remain the target.
