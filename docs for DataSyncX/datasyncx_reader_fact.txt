# DataSyncX reader facts (verified from venv source)

Source: `venv/Lib/site-packages/datasyncx/`.

## Readers exposed (datasyncx.readers.__init__)
AriesReader, FileReader, ImBigDataReader, LamasReader, LargeFileReader,
MongoDBReader/MongoReader, MarsReader, OracleReader, PostgreSQLReader,
SapHanaReader, SharePointReader, SQLServerReader/SqlServerReader,
TeradataReader, XeusReader. **No OasysReader exists.**

## MarsReader — MARS only
`MarsReader(*, username=None, password=None, db_account=False)`
`.read(site, query, **kwargs)` → calls `query_mao(query, site, 'MARS', factory=kwargs.get('factory',''), ...)`.
- `database='MARS'` is hardcoded.
- `query.replace(":site", site)` is done inside.

## OracleReader — generic Oracle (use this for OASYS)
`OracleReader(*, sites=None, username=None, password=None, database=None, node=None)`
`.read(site, query, **kwargs)` → calls `query_oracle(acc=username, pwd=password, node=f'{site}.{database}' if node is None else node, sql=query)`.
- For OASYS: `OracleReader(database='OASYS').read(site, sql)` → connects to `KM.OASYS`.
- No schema substitution happens (`get_mars_schema` returns sql unchanged when database != 'MARS').

## query_mao schema substitution (utils/oracle_db.py)
Hardcoded `schemas` dict:
```
CDDP=A46_PROD_11, AFODP=AAL_PROD_1, KMDP=A15_PROD_21, AFO=AAL_PROD_1,
CD=A48_PROD_21, PG=A12_PROD_0, KM=A15_PROD_21, KM8=A88_PROD_21,
VN=A90_PROD_21, ATD=A43_PROD_0, F21=F21_PROD_21, F21DP=F21_PROD_21
```
Applied only when database == 'MARS'. Substitutes BOTH `:schema` and `@[]@` with the matching schema.

**Implication:** for MARS aliases the emitted SQL should use `@[]@TableName`, NOT `{NODE_MAP[site]}.TableName`. DataSyncX handles the schema mapping. Our hard-coded NODE_MAP is redundant for MARS.

## query_oracle (used by OracleReader)
`query_oracle(acc, pwd, node, sql)` — splits node on '.' to extract site/database, runs `oracledb.connect(user=acc, password=pwd, dsn=node)`. No schema substitution.

## Discriminating MARS vs OASYS from VG2 alias fields
- Both have `DATABASETYPE: Oracle`.
- OASYS hints in EPX_SKIP_CSAM.VG2 alias `a1`:
  - `SINGLESCHEMA: "N/A"` (MARS has `Default`)
  - `PROMPT-TEXT` mentions "OASys"
  - `LOGICALVIEW` starts with `P_` (OASYS convention) vs `F_` (MARS convention)
- Reference SQL `EPX_SKIP_CSAM_SQL.txt` confirms `/NODE=KM.OASYS` for `P_SPC_Chart_or_Raw_Data`.
- Best heuristic: prefix of LOGICALVIEW (`F_`=MARS, `P_`=OASYS) backed by SINGLESCHEMA="N/A".

## SPF logical view expansion gap
- SPF logical view names like `F_Lot_History_v3` and `P_SPC_Chart_or_Raw_Data` are NOT real Oracle views — SPF expands them client-side into physical FROM + intra-view JOINs + implicit WHERE.
- The VG2 carries `physical_table` and `expression` (`a0->p.prodgroup3`) for each column/filter, so we know WHICH physical tables and WHICH sub-aliases (f0,p,v1,v2,v3) are referenced.
- The VG2 does NOT carry: intra-view JOIN keys, implicit WHERE, bridge sub-aliases (e.g. `v2` is needed for v1↔v3 but never appears in columns/filters).
- Fix: hand-maintained view-expansion registry (YAML) for the views the team actually uses.
