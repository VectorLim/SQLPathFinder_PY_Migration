DataSyncX ETL Agent Playbook
This playbook is the durable knowledge base for the repository-local DataSyncX ETL Agent.
Use the agent as the default ﬁrst choice when the task is any of the following:
write or review an ETL script that may use DataSyncX,
decide whether an ETL behavior belongs in a product repository or in DataSyncX,
design batching, query parameterization, task splitting, or runtime metadata ﬂow,
evaluate the minimum safe validation gate for an ETL change.
The agent should stay thin. Put stable ETL-routing rules, evidence order, and DataSyncX-
speciﬁc operating guidance here so the agent can read and apply them instead of carrying all
detail in the prompt body.
Default ETL Entry Rule
When an ETL-writing request could reasonably use DataSyncX, prefer the DataSyncX ETL
Agent over a generic coding agent.
This rule is about decision quality, not repository ownership. The agent may conclude that
the ﬁnal patch belongs in a product repository, but it should still be the ﬁrst ETL reasoning
surface because it knows the framework abstractions, reuse boundaries, and validation
expectations.

DataSyncX-First Decision Rules
Prefer existing DataSyncX abstractions before inventing local framework-like helpers.
Check these levers ﬁrst:
Task and TaskExecutor for orchestration.
TaskRangeBuilder variants for batching, windowing, and split execution.
QueryBuilder or job-spec metadata for parameterized SQL.
Existing readers, writers, and processors before custom wrappers.
Direct demo copy or demo-factory generation before creating a new script shape from
scratch.
Keep the change product-local when the behavior is tied to one product’s source schema,
target schema, predicate, schedule, credential ﬂow, or business rule.
Move the change into DataSyncX only when the capability is broadly reusable and the
repository can support it with focused tests plus adjacent regression coverage.

Minimum Working Procedure
For each ETL task, do this in order:
1. Identify the active repository, branch, runtime path, and current local changes.
2. Freeze the validation baseline: active slice, watermark, sample input, or expected runtime
shape.
3. Classify the task as product-local, framework-worthy, documentation-only, or validation-
only.
4. Find the nearest existing DataSyncX pattern before proposing new structure.
5. Choose one bounded candidate path.
6. Make the smallest safe edit set.
7. Run the narrowest validation that can falsify the approach.
8. Report residual risk and the next exact validation step if any environment-gated checks
were skipped.

Use this ﬂow for user-facing execution:
1. Generate

Free-Style Performance Advisory
For free-style path, provide optional topology guidance with dual triggers.
1. Proactive trigger
Always include one lightweight recommendation for multi-thread batch read plus
bounded single-queue write.
1. Reactive trigger
Escalate guidance when symptoms appear: queue-depth pressure, writer latency
dominance, connection churn, or unstable throughput.
1. Safe defaults
Moderate queue maxsize.
Flush rows aligned with writer chunk behavior.
Bounded retry and deterministic worker shutdown.
1. Boundary
Keep framework-level guidance generic.
Keep product business semantics in product repos.

“Which range mode should we apply: time, token, or none?”

1. “relative time expressions, such as current_time - 12h, current_time - 2d, or date-only
current_date - 7d”
2. “absolute start/end values passed in by the caller or scheduler”

Validation Rules
Treat each implementation as a controlled change with scope, risk level, validation evidence,
docs impact, and rollback note.
For runtime changes under src/datasyncx/**:
run targeted tests for the touched module,
run adjacent regression tests for the same public behavior,
run an integration slice when one exists and the environment is available.
If integration prerequisites are missing, report skipped and name the missing prerequisites
explicitly.
For docs or agent-customization changes:
validate markdown/frontmatter shape,
validate links and docs navigation,
update docs/changelog.md.

Safety Boundaries
Do not:
blur product-repository commits and DataSyncX commits,
claim behavior preservation without a ﬁxed validation baseline,
introduce inline credentials or insecure defaults,
add import-time I/O or network eﬀects,
swallow exceptions broadly without a bounded reason.
In generated or reviewed DataSyncX code, treat plaintext password literals as defects. Prefer
get_config_value(...) or an existing reader/writer auto-resolution path when the component
already derives credentials from the conﬁgured account.
